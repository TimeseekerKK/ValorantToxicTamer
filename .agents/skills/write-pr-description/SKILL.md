# PR 内容规范

仅适用于 ValorantToxicTamer 本项目。让不了解聊天背景的审阅者也能理解：为什么改、改后会怎样，以及哪些结论已有验证。

## 获取依据

- 优先遵从用户当次要求，再读取目标仓库适用的 AGENTS.md、PR 模板和贡献指南；不同目标分支有不同约定时，以目标分支的适用约定为准。
- 根据任务范围读取实际 PR 差异或相对目标分支的差异，必要时查看相关实现和提交记录。区分已纳入 PR 的改动与尚未提交的工作区内容，避免把后者写成已有 PR 内容。
- 结合实际执行记录、CI 结果和用户明确提供的信息说明验证情况。已有可靠记录时，不为填写描述重复运行检查；需要额外验证时，按原任务范围处理。
- 无法获取差异或结果时，利用现有材料写出有依据的部分，并标明影响结论的具体信息缺口。只有缺失信息会改变主要内容且无法自行获取时，才向用户澄清。

## 标题

- 默认使用简体中文，保留代码标识符、产品名和必要技术原文；用户或仓库明确要求其他语言时遵从，不默认添加双语。
- 直接描述最终改动或行为结果，例如“feat:修复导入预览期间仍可编辑消息的问题”，避免“优化代码”“完善功能”等无法判断变化的标题。
- 标题必须带英文类型前缀，采用 `type:描述` 格式，使用英文冒号，冒号后不加空格。常用前缀包括 `feat`、`fix`、`docs`、`refactor`、`perf`、`test`、`build`、`ci`、`chore`；按主要改动选择，用户明确指定前缀时遵从。
- 需要标注 scope 时使用 `type(scope):描述`；不把分支名、版本号或提交哈希机械加入标题。
- 标题围绕本次主要变化，不罗列所有文件或次要调整。

## 正文

- 先交代具体问题和修改后的行为；修复类改动适合用触发条件及修改前后的表现解释。
- 只说明最终实现中与审阅有关的变化和原因。必要时补充影响范围、关键设计取舍、兼容性、迁移要求及已知限制；没有相关内容时省略。
- 篇幅随复杂度调整：小改动通常用一两段加验证情况即可；较复杂改动再使用小标题或列表。不为固定栏目补空话，不逐文件复述 diff。
- 围绕最终范围重写标题和正文。省略聊天过程、代理执行过程、放弃的方案及无关提交；只有能解释当前取舍时才提及备选方案。
- 遵循已有 PR 模板，保留其必要栏目和声明。普通已核实的检查项可按事实填写；需要作者本人确认的声明不代勾。
- 只关联已确认相关的 issue。使用会自动关闭 issue 的措辞前，确认改动确实解决该问题，并符合用户意图和仓库约定；否则使用普通关联。
- PR 正文按审阅需要保留验证和实现依据；Release notes 的专属格式不直接套用到 PR 正文。

## 事实与验证

- 每项行为、修复和测试结论应能追溯到实际差异、执行结果或明确提供的证据；不编造测试次数、性能收益、覆盖率、兼容性或问题编号。
- 区分已实现、已提交、已推送、已发布和已验证。不把计划写成结果，不将与当前改动无关或早于相关改动的检查描述为当前验证。
- 分别说明静态检查、单元测试、构建、桌面交互、真实设备或游戏内验证的结果。仅通过单元测试或构建时，不宣称真实使用场景已验证。
- 验证说明简短、可核查：写明实际检查及结果；只在有记录时添加数量、命令或结果链接。
- 对影响审阅判断的失败、未完成或未执行的关键验证直接说明，不用“全部通过”掩盖范围限制。失败原因只有证据支持时才作归因。

## 输出与操作边界

- 仅请求文案时，交付可直接使用的标题和正文；更新已有 PR 时，按用户指定范围修改并保留范围外内容。
- 创建或更新远端 PR、提交、推送和合并等操作按用户当次或已有明确授权执行。仅请求文案不授权合并；已授权的软件 PR 合并完成后，按下方规则继续发版，已有授权时不重复要求确认。
- 维护本 skill 只修改其相关文件，不因此触发项目升版、打包或发布。

## 合并后的升版、打包与发布

- 软件 PR 合并到本仓库发布分支后，默认继续完成“审核合并结果 → 预检远端版本 → 修改版本号及 README → 测试 → 重新打包 → 提交推送 → 发布新版”的流程。该后续流程已获用户授权，无需逐项重复询问；用户明确要求暂不升版、打包、推送或发布时按其限定执行。
- 先从远端确认 PR 已合并、实际合并提交及目标分支，核对发布源码已包含合并结果。以合并后的目标分支源码和更新后的版本重新构建，不使用 PR 合并前的旧产物。
- 执行前读取并遵循 [review-and-bump-version](../review-and-bump-version/SKILL.md)。版本级别、正式版基础号、Beta 序号、分支与发布渠道、Beta 转正式版、重试及同批次去重规则均以该 skill 为准；复用其版本预检脚本计算版本，不在本 skill 另设计算规则，也不根据 PR 的 feat/fix 前缀直接决定版本级别。
- 后续的版本与 README 同步、测试、重新构建、提交推送、标签、Release 正文与附件及发布后核验，完整执行该 skill 的流程。新产物必须对应合并后的发布源码、目标版本和渠道；检查或构建失败时先处理阻塞，不宣称已经发布。
- 同一批改动已完成目标版本发布时，先核实源码、版本、渠道和附件，复用已完成步骤，不因 PR 合并重复升版发布。纯分支同步、仅维护 skill 或其它与软件无关的改动，遵循该 skill 的不发版例外；用户明确要求发布时按指定范围处理。
- 仅更新此规则不会合并任何 PR，也不触发软件升版、打包或发布。

## 简短示例

下例仅演示组织方式；具体行为和验证必须替换为当前任务的真实情况。

标题：feat:修复导入预览期间仍可编辑消息的问题

正文：

导入预览打开期间，用户仍可修改消息列表，导致预览结果与最终导入状态不一致。

本次调整将编辑操作锁定到预览结束，并在确认导入时重新检查重复消息，避免重复写入。

验证：
- 导入相关单元测试通过。
- 尚未进行桌面交互验证。
