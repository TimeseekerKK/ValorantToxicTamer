# 审核改动并更新版本

适用于当前 ValorantToxicTamer 仓库。完成一次修改任务后主动执行，无需用户重复要求。用户明确限定只审核、暂不升版或暂不打包时，遵从该范围并说明未完成的同步项。

## 升版前提

先判断本次改动是否涉及软件本身，再决定是否执行版本计算、版本同步和 EXE 构建。

- 如果全部改动都与软件功能、运行行为、界面、配置、数据、运行依赖、构建分发及使用说明无关，可以保持版本号不变。例如只修改仓库介绍、开发协作规范、skill、内部记录或未随软件分发的素材。
- 按实际影响判断，不能仅按文件名或目录判断。例如 README 中的仓库介绍调整可以不升版，而软件使用说明的修正仍按软件相关改动审核。
- 同时包含软件相关与无关改动时，只依据软件相关部分判级；无关部分不抬高更新级别。
- 判断无需升版时，简述原因，结束本 skill 的升版流程；不为此修改源码或 README 的当前版本号，也不触发 EXE 重打包。用户明确要求升版时，按其要求执行。

## 审核与判级

1. 确认仓库根目录及适用的 AGENTS.md。查看 `git status --short`、暂存和未暂存的 diff，并检查本次新增的未跟踪文件。结合任务开始时的状态区分本次改动与用户已有改动，不把无关修改纳入本次版本。
2. 审核实际行为、兼容性、配置和数据迁移、界面交互、构建及文档是否一致。按需要运行已有检查；发现本次改动引入的问题，在已授权范围内修复，再判定最终级别。未解决的问题影响交付时，说明阻塞，不能声称已完成发布准备。
3. 根据最终改动的用户影响判级，不按文件数、代码行数或提交类型机械判断。混合改动取最高级别，并简要说明依据。

| 级别 | 判定依据 | 示例 |
| --- | --- | --- |
| 重大更新：x | 核心使用方式或架构大幅改变；不兼容的配置、数据或接口变化；用户需要迁移或重新学习主要流程 | 不兼容的数据格式迁移、核心发送流程整体重构并改变使用方式 |
| 中等更新：y | 新增完整功能、明显扩展现有能力或较大界面改版，整体保持兼容 | 新增更新功能、新增消息管理能力、设置页较大改版 |
| 小更新：z | 局部缺陷修复、性能优化、小范围界面调整、文案或文档修正，以及不改变外部行为的维护 | 修复快捷键时序、修正文案、调整按钮间距 |

## 版本计算

对外格式严格为 `vx.y.z`，三段均为非负整数；源码中的 `VERSION` 使用不带 `v` 的 `x.y.z`。

- 重大更新：`v(x+1).0.0`。
- 中等更新：`vx.(y+1).0`。
- 小更新：`vx.y.(z+1)`。
- 只增加选定的一段且加 1，其后的所有段归零；不按十进制进位，例如 `v1.2.9` 小更新后为 `v1.2.10`。
- 例如从 `v1.4.7` 出发：重大更新为 `v2.0.0`，中等更新为 `v1.5.0`，小更新为 `v1.4.8`。
- 以本次任务开始前的版本为基线，同一批修改只升一次；重试打包、重复审核、修复该批问题都沿用目标版本。若该批已升版，检查并补齐同步项，不重复累加。
- 没有实际改动时不升版；仅无关软件的改动可以不升版，按「升版前提」判断；仅维护 `.agents/skills/` 时默认不触发应用发版。确需调整已升版本的级别时，从原基线重新计算。

## 同步源码、README 和 EXE

当前项目的版本和构建入口如下，执行时核实文件仍然适用：

- `valorant_toxic_tamer/app_version.py` 的 `VERSION` 是应用版本来源；主程序、界面和更新检查引用该值。
- 更新 `README.md` 标题及其他表示**当前版本**的内容，展示为 `vx.y.z`。按改动同步受影响的使用说明；保留历史版本记录、示例版本号和测试样例。
- 修改版本后，通过项目已有脚本重新生成 `dist/ValorantToxicTamer.exe`。不能仅重命名旧 EXE 或仅修改 README；EXE 文件名保持项目约定，版本来自新构建包含的代码。
- 如果构建已配置 Windows `FileVersion` / `ProductVersion`，同步对应的版本资源（四段数字形式用 `x.y.z.0`）。若未配置，明确区分应用内版本与 Windows 文件属性，不能声称文件属性已更新。

在仓库根目录使用现有环境，依次执行：

```powershell
.\.venv\Scripts\python.exe -m unittest discover -s tests -v
.\scripts\build.ps1
```

`scripts/build.ps1` 当前已包含 `tests/check_package.py` 的打包检查；若脚本调整，以实际入口为准。构建前确认目标 EXE 是否正被占用，不擅自结束用户正在使用的进程。缺少环境、文件占用或构建失败时说明具体原因和已完成的部分，修复可恢复问题后沿用原目标版本重试。

## 核对与交付

- 确认源码与 README 的当前版本一致，构建及打包检查成功，EXE 为本次版本修改后生成。
- 通过项目可用的产物检查方式或运行新 EXE，核实其中的应用版本；若只能确认构建来源，准确注明运行时版本尚未验证。自动测试和静态检查不等于真实游戏验证。
- 检查最终 diff，避免修改与当前版本无关的数字、测试中的示例标签或用户个人数据。
- 交付时说明判定级别和依据、旧版 → 新版、README / EXE 的同步状态、实际检查结果及剩余问题。更新 EXE 仅指本地构建，不包含自动提交、推送、打标签或发布 GitHub Release。
